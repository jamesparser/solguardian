Why it is explainable

  • Multi-agent, and provably order-independent. One hunter per file shard runs concurrently, then an adjudicator cross-checks and a writer gates the output contract. Serial, threaded and process-parallel runs return byte-identical findings (24-contract corpus, medians: 5.1 s → 4.5 s → 2.0 s), so parallelism cannot change a report.
  • Skill packs, not vibes. Each finding cites the checklist in skills/ it enforced and lists the items it satisfied — you can argue with the rule.
  • Comments cannot create findings. Every detector matches a masked copy of the source where comments and strings are blanked at equal length.
  • One root cause, one finding. Packs hand off deliberately (a delegatecall bug belongs to the proxy pack, not access control), and each exclusion has a regression test.
  • Deterministic. Nothing in the scan path calls a model, so a clean run costs nothing and CI can gate on it: --fail-on high exits 1.
Heuristic tool, honest limits. Expect false positives on unusual-but-correct code and false negatives on anything the patterns do not describe. No symbolic execution, no bytecode, no cross-contract data flow, no deployed state. The 17/17 figure is measured against a seed set we wrote — it is a floor, not a benchmark. A clean SolGuardian report is not an audit.

Built with IBM Bob 2.0

Bob IDE is the development environment: /init + AGENTS.md, Agent-mode multi-file work, parallel subagents for the EVM and Solana detectors, document understanding over the skills/ packs, and the review / commit flow. The same split ships in the product — solguardian/agents/ runs EvmHunter and SolanaHunter concurrently, then ReportWriter enforces the finding contract. Task evidence and the verbatim prompts are in bob_sessions/.
